**建议做成“同一套仇恨重定向逻辑＋三个输入入口”：R 甩怪、T 接怪、F 放假人。**这一轮只验证“改变怪物流向，能否让走位和多人配合更有趣”，不加入魅惑伤害、成长、减伤、奖励或完整技能树。

我检查了当前项目的目标选择、模拟交接、屏幕范围和敌人离屏处理代码。**现有基础可以复用，但有一处必须调整：目前更换仇恨目标时，会同时把模拟权交给新目标玩家，尚不支持你要求的“先换仇恨，进入对方屏幕后再交接”。**

下面给出最小可行方案。本轮仅做方案核查，没有修改项目。

## 一、先明确两件不同的事：怪物追谁，由谁计算移动

假设 A 使用 R，把怪物甩给 B：

| 阶段 | 怪物追谁 | 谁负责模拟 |
|---|---|---|
| 使用前 | A | 原模拟者，例如 A |
| R 生效后，还没进入 B 的画面 | **B** | **仍由原模拟者计算** |
| 进入 B 的画面，完成交接后 | B | **B 的客户端** |

**怪物应当立刻转向新目标，但继续从当前位置走过去，不能瞬移到对方屏幕。**

对于 T，我建议将你的屏幕条件统一解释为：

> **进入“新的仇恨目标玩家”的屏幕后交接。**

也就是 A 使用 T，把 B 的怪吸引过来：怪物立刻追 A，进入 **A 的屏幕**后，再交给 A 模拟。不是进入原目标 B 的屏幕后交接。

F 则是：

```text
原来追 A
→ 暂时追 A 留下的假人
→ 5 秒后重新追 A 当前所在的位置

整个正常过程保持原模拟者不变
```

项目的 `EnemySimulationAssignment` 已有分开的 `AggroTargetPlayerId` 和 `SimulationOwnerPlayerId` 字段，因此不需要从零设计网络身份体系。  
*代码依据：`Assets/_Project/NetworkCombat/Contracts/EnemySimulationContracts.cs`。*

## 二、三个技能的首版规则

### 共同规则：只处理施法当时的一批怪

为了让效果容易理解，也控制实现范围，建议首版统一采用：

| 项目 | 原型默认 |
|---|---|
| 测试目标 | 普通、存活、已经初始化的敌人；暂不包含精英和 Boss |
| 每次影响数量 | 最多 **10 只**，可调 |
| 影响范围 | 原仇恨玩家**当前屏幕内**的合格敌人 |
| 选择顺序 | 优先距离原仇恨玩家最近的敌人 |
| 作用方式 | 施放时选定一次，不持续吸引之后新生成的怪 |
| 技能冷却 | R、T、F 各自 **20 秒**，作为初始试玩值 |
| 对战斗的影响 | 不造成伤害，不修改 HP，不改变掉落和经验 |
| 施法操作 | 按下瞬间触发，不锁移动，不停止自动攻击 |

这里的“自己的怪”必须按**仇恨归属玩家**判断，不能按模拟者判断。例如，怪物已经追 B、但尚由 A 模拟时，它应当算“B 的怪”。

F 期间保留基础玩家归属：这批怪仍属于 A 的仇恨组，只是临时追 A 的假人。这也方便处理后续 R、T 的覆盖。

### 1. R：把自己的怪转给队友

假设施法者为 A，选中的队友为 B：

> 从当前追 A、位于 A 屏幕内的普通怪中选最多 10 只，将其仇恨目标改为 B。

生效后，A 可以利用怪物转向产生的空间离开；B 则需要处理即将到来的压力。

**仇恨转移不设自动到期。**因为你只给 F 指定了“5 秒后回来”，R 暂按真正换目标处理：除非被其他技能再次修改、目标失效或发生正常重选，否则继续追 B。

模拟权按前面的规则延后交接。已经位于 B 屏幕内的怪，可以立即进入交接流程；不需要先退出画面再进入。

没有合格队友或没有可转移目标时，显示原因，不消耗冷却。

### 2. T：把队友的怪转到自己

A 选中 B 后按 T：

> 从当前追 B、位于 B 屏幕内的普通怪中选最多 10 只，将其仇恨目标改为 A。

**R 和 T 不需要两套实现。**它们只是同一个操作的方向不同：

```text
R：来源玩家 = 自己，接收玩家 = 选中队友
T：来源玩家 = 选中队友，接收玩家 = 自己
```

仇恨立即改变，怪物进入接收玩家 A 的画面后再交接模拟权。

本轮不要额外给 T 添加护盾、减伤或伤害加成。先观察：**救队友、主动聚怪，是否已经足以让玩家愿意使用它。**否则很难分辨乐趣来自“接怪”，还是来自额外奖励。

### 3. F：原地留下一个 5 秒假人

建议假人采用最简单的占位表现：

> 在施法者脚下留下一根柱子或一个圆形标志，原地不动，显示 5 秒倒计时。

施放时选取当前追自己、在自己屏幕内的最多 10 只普通怪，让其追向假人。玩家则可以移动离开、调整站位或趁机输出。

| 假人行为 | 原型规则 |
|---|---|
| 是否跟随玩家 | **不跟随**，留在施放位置 |
| 是否有 HP | 没有，固定存在 5 秒 |
| 是否造成伤害 | 不造成 |
| 是否阻挡单位 | 不阻挡 |
| 是否持续吸引新怪 | 不吸引，只影响本次选定的怪 |
| 是否改变模拟者 | 不改变 |
| 是否让玩家无敌 | 不会；玩家仍可能受到碰撞和既有攻击伤害 |
| 到期后的目标 | 施法玩家当前的位置，不是施放时的位置 |

假人不必成为完整的角色，不要给它接上玩家 Build、GAS 血量、装备或死亡系统。它只需要一个**可同步的位置、身份和到期时间**，作为敌人的临时追踪目标。

每人最多一个假人；调试时提前再次施放，应替换旧假人，不叠加。

## 三、最小实现：复用现有交接，补上“目标与模拟者分离”

### 1. 不能直接把现有换目标接口接到 R、T 上

目前的调用关系是：

```text
RequestTargetChange
→ CommitTarget
→ AssignClientOwner(enemy, target, target)
```

最后两个 `target` 分别表示模拟者和仇恨目标，也就是**换仇恨时一起换模拟者**。

因此，需要在现有 World／Agent 中补充两个清晰的操作，而不是再建一套 AI：

| 拟增加的操作 | 职责 |
|---|---|
| **改变目标、保留模拟者** | R／T 生效时修改追踪目标，不立即启动模拟交接 |
| **将模拟交给当前仇恨玩家** | 新目标玩家看到该怪物后，走现有交接流程 |

还有一个容易遗漏的点：当前接口会把“目标没有变化”的请求视为无需处理。R 已提前把仇恨改成 B 后，后续接管不能再次只判断“目标是否已经是 B”，而应判断：**模拟者是否仍不是 B。**

*代码依据：`NetworkEnemySimulationWorld.Handoff.cs` 的 `RequestTargetChange`、`CommitTarget`；`Server/EnemyHandoffProgress.cs` 的 `Request`。*

### 2. F 只增加一层临时目标覆盖

建议让敌人的最终追踪目标统一由一个入口解析：

```text
有有效假人覆盖 → 追假人
没有假人覆盖   → 追仇恨归属玩家
```

**不要每帧单独写一次 `EnemyController.Target`，然后让原网络逻辑继续写另一遍。**当前 Agent 会同时更新敌人移动目标和攻击脚本目标，假人必须接入同一个目标解析入口，否则可能出现“移动追假人，攻击却仍瞄准玩家”，或覆盖被刷新掉的问题。

这层覆盖只保存假人、施法来源、版本和截止时间，不增加仇恨分值表、状态堆栈或通用嘲讽系统。  
*代码依据：`NetworkEnemySimulationAgent.cs` 的 `ApplyAssignment`、`ResolvePlayerTarget`。*

### 3. 仇恨变化不应重启敌人动作

目标更新建议使用独立版本，不把每次目标变化都当成完整模拟交接。

R／T／F 生效时，**只改变后续追踪和下一次攻击选择**；已经开始的冲刺、近战前摇、攻击和击退继续按原规则完成，不重播、不重置冷却。

当前真正交接已经有位置、动作和击退恢复逻辑，跨屏接管时继续复用它。  
*代码依据：`NetworkEnemySimulationAgent.Handoff.cs` 的 `ApplyHandoff`、`RestoreSimulationKnockback`。*

这里调整的是项目自己的 `SimulationOwner`，**不是给敌人调用 Mirror 的 `AssignClientAuthority`**。Mirror 的对象所有权会影响 Command 权限等行为，不能把它和你当前的敌人模拟分工混为一谈。:chatgpt-content-reference{index="0"}

## 四、“进入另一个玩家屏幕”怎样做得足够简单

### 用新目标玩家自己的游戏摄像机判断

建议每个玩家约 **0.1 秒**上报一次自己的游戏视野范围。服务器只对正在等待交接的怪物检查：

> 怪物身体范围与新目标玩家的视野范围相交，并且该玩家、怪物和视野报告仍有效，就发起交接。

视野计算可以复用现有的 `GameplayCameraGeometry.ViewBounds`。但不能把服务器根据角色位置估算出来的画面，直接当成远端玩家的实际画面；当前刷怪逻辑对远端视野确实存在估算路径。  
*代码依据：`Gameplay/Combat/CameraFX/GameplayCameraGeometry.cs`；`NetworkGameplayEnemySpawner.Reference.cs` 的 `ReferenceView`。*

**不建议使用 `Renderer.isVisible` 判断“被 B 看见”。**它表示被任意摄像机认为可见，在编辑器中也可能被 Scene 窗口摄像机影响，不能表达指定玩家的游戏视野。:chatgpt-content-reference{index="1"}

原型只需要规定：

- 两人都看见时，交给**指定的新仇恨目标**，不是交给任意看到它的人。
- 每次仇恨转移最多完成一次正常交接；交接后走出屏幕，不自动交回，避免边缘来回切换。
- 视野报告缺失或过期时，不触发交接，原模拟者继续工作；确认交接完成要看新模拟者的有效快照，而不只是字段变了。

### 有一个必须处理的现有干扰：离屏回收／重定位

当前项目会对符合条件的离屏怪物进行回收或重新摆放。**R／T 的怪物在两名玩家之间行走时，不能被这套逻辑突然移到另一处，否则测试的就不是“转移怪物流向”。**

建议只对本轮受影响的怪物做一个小例外：

> 等待跨屏接管期间，以及假人覆盖有效期间，暂不执行普通离屏重定位；状态结束后恢复。

不需要全局关闭离屏优化，也不要修改其他怪物的规则。  
*代码依据：`NetworkGameplayEnemySpawner.Reposition.cs` 的 `UpdateReferenceReposition`。*

## 五、三个技能相互覆盖时，只保留一条规则

**每只怪物以服务器最后接受的有效目标修改为准。**

这条规则足以避免为原型设计复杂优先级：

| 情况 | 原型处理 |
|---|---|
| A 用 R 转给 B，随后 B 用 R 转给 C | 改为追 C；旧的“等待交给 B”请求失效 |
| A 放假人，随后 B 用 T 把这批怪接走 | 改为追 B，同时解除对应假人覆盖 |
| 旧假人 5 秒到期 | 只解除仍属于该次施法的覆盖，**不能把已被 R／T 转走的怪强行拉回** |
| F 生效时，这批怪原本还有待完成的跨屏交接 | 暂停这批怪的技能性交接；F 到期后按仍有效的目标继续判断 |
| 目标玩家死亡／断线 | 撤销失效的目标意图，走正常重选与兜底 |
| 怪物死亡、回收或换局 | 删除对应临时记录，不向后续复用对象补发旧效果 |

F 的“5 秒后回来”应当实现为**解除自己的临时覆盖**，而不是“计时结束后，无条件把目标写回 A”。

另外，拆开仇恨和模拟者后，要新增一个必要检查：**原模拟者是否仍在线可用。**例如怪物追 B、仍由 A 模拟时，A 断线了，就不能因为 B 仍存活而遗漏接管。紧急断线兜底优先于正常的屏幕交接条件；这不算 F 主动转移模拟权。  
*当前检查基础见 `NetworkEnemySimulationWorld.Handoff.cs` 的 `UpdateTargetDecisions`。*

## 六、按键、反馈和调参

### 按键：魅惑与暴食先互斥

当前 R 已绑定暴食矩形标记。建议原型面板增加一个简单选择：

```text
原型模式：关闭 / 暴食 / 魅惑
```

选择魅惑时，关闭暴食主动和被动，避免一个 R 同时触发两套技能，也避免怪物还没被转移就被吞掉。保留原有 Q、Shift、E 和选卡输入。

这轮先用两名真实玩家验证，R／T 自动选另一人。需要三至四人时，再在调试面板里提供一个队友下拉框，并在 HUD 常驻显示选中的玩家，不占用已有选卡数字键。

### 反馈：先让双方都知道发生了什么

不需要正式角色动作，下面这些就足够：

| 反馈 | 最小表现 |
|---|---|
| R／T 命中目标 | 受影响怪物短暂闪一下，显示新目标玩家的简称 |
| 接收者通知 | 例如“P1 转来了 8 只怪”或“P1 帮你接走了 6 只怪” |
| F 假人 | 简单柱子／圆形 Sprite，显示剩余秒数 |
| 技能 HUD | R／T／F 冷却、当前选中队友、本次影响数量 |
| 开发调试 | 分别显示“仇恨目标”“实际追踪目标”“模拟者”“待交接状态” |

**仇恨已转移与模拟已交接，应当在调试中分开显示。**否则容易把“怪物确实转向，但还在等跨屏”误判为失败。

参数集中保留：三个冷却、最大影响数量、假人持续时间，以及各技能开关。默认 F 为你要求的 **5 秒**；不再加入额外的魅惑强度、概率、持续伤害或仇恨倍率。

## 七、怎样试玩，才能判断是否值得继续做

**R 和 T 至少需要两名真实联网玩家。**单人 Host 只能验证 F 和部分规则，不能证明多人甩怪／接怪体验成立。

建议先用同一段普通敌人战斗，分别测试“关闭”“只开 R”“只开 T”“只开 F”，最后再组合；保留正常武器、伤害、掉落和选卡。

| 场景 | 要观察的机制 |
|---|---|
| 两人靠近、画面重叠 | R／T 能否立即改变局部包围和站位 |
| 两人分开约一屏 | 怪物是否真的走向新目标，途中连续移动，进入新目标画面后正确交接 |
| A 被围，B 使用 T | B 是否有主动救援或聚怪的动机，A 是否获得可利用的脱身空间 |
| A 使用 R | A 的脱身是否有选择，B 能否理解并应对，而不是毫无预警地受罚 |
| A 使用 F 后侧移 | 是否能借 5 秒改变包围形状、聚怪或重新站位，而不只是多了一个装饰 |
| F 期间穿插 R／T | 到期是否尊重新目标，没有错误回拉或重复交接 |

特别需要区分三个判断：

**R：**“甩给别人很爽”不等于多人体验整体更好。要同时看接收方是否觉得有应对空间；否则它可能更偏欢乐互坑，而不是合作救援。

**T：**若玩家完全不愿意主动承担这批怪，先判断是否缺少救援、集中清怪的实际场景，不要立即用大量增伤奖励把问题盖住。

**F：**若玩家在假人存在时仍然原地不动，只靠武器输出，可能验证的是短时吸引火力，而不是走位创新。这未必无趣，但应当准确知道它带来的是什么。

技术验收则重点覆盖：旧模拟者持续移动、新模拟者首个快照被服务器接受、屏幕重叠不反复交接、重复消息不重复施法、F 到期不覆盖新目标，以及断线后没有无人模拟的怪物。

### 本轮边界

本轮只做**目标重定向、延后模拟交接、5 秒假人、基础反馈、参数调整和双人正常战斗试玩**。不做仇恨分值系统、完整魅惑状态树、假人血量、魅惑增伤、技能成长、正式角色差异或完整技能重连存档。

**最关键的验证不是“字段从 A 变成 B”，而是玩家是否开始通过“把哪批怪引向谁、何时留下假人、随后往哪里走”作出新的选择。**

执行前只需确认一处语义：**A 使用 T 接走 B 的怪时，是否按“怪物进入 A 的屏幕后，把模拟交给 A”处理？上面的方案按这个对称规则设计。**
